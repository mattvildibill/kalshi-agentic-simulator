# Kalshi project audit — October 29, 2026

## Conclusion and scope

The experiment has sound core controls, but operational freshness and research discipline needed improvement. The active ledger reconciled exactly at inspection. The strongest substantive limitation is that none of the seven entry forecasts had positive expected value at its own recorded low estimate, and there were no resolved outcomes from which to infer forecasting skill. Positive central expected value alone does not establish a reliable advantage.

Reviewed baseline: `78d0697` (the reference redesign). Scope included all application routes and components, accounting/execution/settlement, Supabase storage and run isolation, public/private API boundaries, CLI behavior, research instructions and published briefs, dependency security, desktop/mobile interactions, release checks, and live API reads. This audit did not place trades, settle holdings, publish replacement forecasts, reset runs, or change the 10% server caps. Source availability was sampled; the underlying economic forecasts were not independently re-researched to authorize new investments.

## Research quality assessment

All seven entry briefs had positive central modeled EV but negative low-case EV at their recorded costs. The individual stress losses ranged from $3.73 to $730.78. These calculations use the authors' sensitivity ranges; they do not establish that the low cases will occur or that the central forecasts are wrong. They demonstrate that sizing and apparent edge were sensitive to assumptions. The 10% cap is a ceiling, not evidence of adequate conviction.

The Wisconsin brief includes a Nevada statutory citation. The exact resolution rule must be checked against the correct jurisdiction. Do not modify the old brief: publish a new dated correction only after verifying the correct source. Some briefs explicitly rely on uncalibrated Elo perturbations, external forecasts incorporating markets, judgmental probabilities, or indexed secondary reporting. Those limitations are useful disclosures, but they must affect the decision and size rather than only appear as caveats.

Four sampled source URLs (Federal Reserve statement, NHC season table, DDHQ Wisconsin forecast and TennisAbstract WTA ratings) returned HTTP 200 during the audit. This establishes accessibility at that time only, not that every claim is correct or that all quoted material is current. In particular, prefer canonical production NHC materials over an upgrade/staging hostname when verifying final rules and observations.

The [strategy](STRATEGY.md) now sets these operating defaults while calibration is absent:

- Verify exact contract semantics, primary evidence, source access and timestamps before estimating a probability.
- Require a method, a defensible range, the strongest contrary case and a concrete review trigger. Identify circularity in forecasts that already include market prices.
- Evaluate the proposed marginal quantity after fees/slippage at both central and low estimates. Default to watch/pass if the low-case edge is nonpositive; do not adjust forecasts to fit a desired order.
- Begin at 0.25% of initial capital per new thesis; consider up to 1% only with strong evidence and challenge. Default gross budgets are 25% of starting capital total and 10% per related theme. These are instructions for Blue, not newly implemented engine guarantees.
- Preserve all fills and forecasts. Evaluate a predeclared forecast per resolved market, including watch/pass decisions; do not count repeated fills as independent samples. Zero resolutions means calibration and skill remain unknown.

## Security and reliability evidence

The service uses a fixed public Kalshi API origin, rejects ticker/path injection, keeps Blue and Supabase credentials server-side, authenticates before mutations, limits JSON bodies and rejects unknown fields, retains quotes and forecasts, and uses compare-and-swap updates with retries. Run identities are rechecked inside commits; old in-flight operations cannot apply to a replacement run. Exceptional or unsupported settlements remain unresolved. Local storage is refused in production and never replaces a failing live database.

The checked-in SQL enables row-level security and revokes anonymous/authenticated table access. Live application access was healthy, but the dedicated project's database policy configuration could not be independently verified through the currently available management-project mapping. Do not describe the SQL file as proof of the deployed policy.

`npm audit` reported zero known vulnerabilities across installed production and development dependencies at inspection. This is a point-in-time advisory check, not a guarantee of future dependency security. No extra paid infrastructure, model provider, external font dependency, or real exchange-order capability was introduced.

## Operational items that remain unverified or deferred

1. **Blue's actual scheduler:** publishing the policy and task template does not prove that Blue's own scheduled task fetched them. The next authorized scheduled run should record policy version/hash, selected run ID, complete sync evidence, actual scan coverage, decisions and errors. No new schedule or notification stream was created by this audit.
2. **Runtime logs:** Vercel runtime-log queries returned 403 with the connected account during the preceding release verification; no CLI credential is configured. Public/API/browser checks are available, but platform logs were not independently cleared by this audit.
3. **Database access and backup recovery:** confirm the deployed table's RLS/grants in the dedicated project's authorized console and retain a private export. Validate recovery against an isolated environment before relying on backups; no production reset or restore should be used as an audit test.
4. **Calibration analytics:** no settled outcomes exist yet. Implement predeclared Brier/calibration evaluation once there are eligible resolved forecasts; the policy defines exclusions and baseline requirements. Do not invent metrics or a probability confidence score in the meantime.
5. **Historical valuation and scale:** the single JSON row is intentionally simple. It retains current marks and archived runs, not a mark-to-market time series. Before sustained growth, measure payload/read cost and consider paginated research, structured history and incremental backups. Do not imply these capabilities already exist.
6. **Independent evidence corrections:** the next authorized research review should address the jurisdiction mismatch and reassess the existing holdings under the new stress gates. An audit of software is not authorization to rewrite research, sell holdings, or place new trades.
